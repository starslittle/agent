# 启点秋招最小 MVP

> 版本：v0.3
>
> 状态：秋招版 MVP 产品基线
>
> 最后更新：2026-07-30

## 0. 文档目的

本文档定义启点当前真正要完成的最小 Web MVP，是 [`Web MVP 产品需求`](web-mvp.md) 的秋招优先子集。

它同时服务两个目标：

1. 验证启点的核心产品价值；
2. 服务秋招，学习并展示完整的 Agent 技术链路。

长期方向见 [`启点完整产品蓝图`](future-product.md)，父级产品范围见 [`Web MVP 产品需求`](web-mvp.md)，技术实现见 [`Agent Runtime 目标架构`](../architecture/agent-runtime.md)。

## 1. MVP 定义

第一版是一个**能够使用个人上下文、执行 Skill，并在用户确认后更新长期记忆的 Web Agent**。

它只需要跑通一条完整链路：

```text
保存个人信息
→ 提出一个真实问题
→ Agent 选择 Skill
→ 获取相关上下文
→ 调用模型或工具
→ 流式返回结果
→ 产生更新建议
→ 用户确认
→ Wiki 更新
```

MVP 不追求覆盖完整个人 AI 身份系统，也不追求 Skill 数量。

## 2. 双重成功标准

### 2.1 产品成功

证明用户记录过的信息，可以在下一次真实问题中被准确使用，并继续形成长期积累。

### 2.2 秋招成功

项目能够真实展示：

- 一个 Agent 加多个 Skill；
- Skill 路由；
- Tool Calling；
- 上下文组装；
- 会话与长期记忆分层；
- Human-in-the-loop；
- 流式事件；
- Run 状态机；
- 数据持久化；
- 可观察性与失败处理。

## 3. 当前用户与首个场景

当前用户就是产品创建者本人，主要处于秋招和面试准备阶段。

首个真实场景选择：

> 基于个人背景和面试复盘，分析下一轮面试应该优先准备什么。

这个场景可以持续使用和快速验证：

- 当前求职状态会变化；
- 面试复盘适合以 Markdown 导入；
- 历史经历和个人规则会影响建议；
- 建议可以在下一次面试后被验证；
- 使用结果可以继续更新 Wiki。

## 4. 首批 Skill

P0 只正式支持两个 Skill。

### 4.1 决策 Skill

用于秋招、职业、项目和生活中的具体选择。

它需要：

- 读取相关事实、当前状态和个人规则；
- 展示本次使用了哪些上下文；
- 输出选项、收益、代价、反例和未知项；
- 不替用户自动选择；
- 产生一张最小决策卡；
- 可以提出个人信息更新建议。

### 4.2 命理 Skill

复用现有项目能力，用于证明同一 Agent Runtime 可以承载完全不同的领域能力。

它需要：

- 获取出生信息；
- 使用确定性工具排盘；
- 区分排盘事实和 AI 解读；
- 返回可展示结果；
- 只在用户确认后保存长期信息。

### 4.3 通用对话与调研

保留为公共支持能力，但不建设独立产品入口，也不计入首批主要 Skill。

## 5. Skill 触发方式

MVP 同时支持三种入口，但不为每个 Skill 设置永久按钮。

### 5.1 默认：自然语言自动路由

用户直接输入：

> 下一轮面试，我应该优先准备系统设计还是算法？

Agent 自动判断使用决策 Skill。

### 5.2 显式：`/` 命令

输入 `/` 后显示：

```text
/decision    分析一个选择
/fortune     进行命理分析
```

用户也可以直接输入：

```text
/decision 下一轮面试应该优先准备什么？
```

显式指定后，系统不再重新选择主 Skill。

### 5.3 引导：空白页快捷卡片

首次进入可以展示：

- 分析一个决定；
- 导入面试复盘；
- 进行命理分析。

快捷卡片只用于新手引导，不作为长期 Skill 导航。

## 6. Skill 可见性

Skill 可以自动选择，但不能完全隐藏。

回答顶部展示：

```text
决策 Skill
自动选择 · 使用了 4 条个人信息
```

如果由用户指定，则展示：

```text
决策 Skill
由你指定
```

用户可以展开查看：

- 为什么选择这个 Skill；
- 本次使用了哪些个人信息；
- 调用了哪些工具；
- 是否改用其他 Skill 重新运行。

### 6.1 路由不确定性

| 判断 | 行为 |
| --- | --- |
| 高置信度 | 自动选择并执行 |
| 中等置信度 | 建议使用某个 Skill，由用户确认 |
| 低置信度 | 使用普通对话 |

### 6.2 不作为用户 Skill 展示

以下属于内部运行步骤：

- 上下文检索；
- Markdown 解析；
- 冲突检查；
- Memory Curator；
- 记忆写入；
- Artifact 保存。

它们只在 Agent Run 中展示，不出现在 `/` Skill 列表。

## 7. 最小页面

P0 只建设三个主页面。

### 7.1 对话

负责：

- 输入问题；
- 自然语言或 `/` 选择 Skill；
- 流式展示回答；
- 查看本次使用的上下文；
- 查看工具结果；
- 确认信息更新；
- 保存最小决策卡。

### 7.2 我的 Wiki

负责查看和管理：

- 已确认事实；
- 当前状态；
- 个人规则；
- AI 分析；
- 一篇导入的 Markdown；
- 已保存的决策记录。

### 7.3 Agent Runs

负责展示一次运行中真实发生的步骤、状态、工具、结果和错误。

同一套 Run 投影和页面组件支持内部只读观测模式。普通用户只查看自己的 Run；拥有
最小观测权限的内部人员可以跨用户筛选脱敏 Run，用于定位 Skill 路由、模型、工具、
上下文、事件和性能问题。内部模式不提供取消、重放、业务数据修改或原始日志查看。

### 7.4 暂不独立建设

- 决策不做一级页面，先作为 Wiki 中的记录；
- 进化收件箱先放在对话结果和 Wiki 待确认区域；
- Skills 页面暂不建设，Skill 信息通过标签和 Run 展示。

## 8. 最小数据范围

### 8.1 Wiki Item

第一版只区分：

| 类型 | 例子 |
| --- | --- |
| 已确认事实 | 当前准备 Agent 岗位秋招 |
| 当前状态 | 已经完成某公司一面 |
| 个人规则 | 面试准备优先结合真实项目 |
| AI 分析 | 系统设计表达可能是当前薄弱点 |

每条信息至少具有：

- 内容；
- 类型；
- 来源；
- 更新时间；
- 状态；
- 是否经过用户确认。

### 8.2 Markdown Document

第一版只需要支持导入一篇 Markdown，例如面试复盘。

流程：

```text
上传 Markdown
→ 保存原文
→ AI 提取候选事实、状态和规则
→ 用户确认
→ 写入 Wiki
```

MVP 不做批量导入、实时 Obsidian 同步和复杂文档管理。

当前 P0 的 Markdown Document 只支持用户手动导入、查看和管理。Agent 创建、修改
和删除 Document 是已确认的产品目标，但需要独立的 Capability、Revision、
Changeset、删除确认和审计设计；实现轮次尚未决定，不并入本轮导入 Task。

### 8.3 数据原则

- PostgreSQL 是线上事实源；
- Wiki 是数据的用户视图；
- Markdown 是开放文档；
- Runtime Checkpoint 不等于长期记忆；
- 检索索引可以重建，不是事实源。

Wiki 的上下文控制与 Document CRUD 分开处理：

- “暂时遗忘 / 恢复”只允许用户在页面手动操作，不暴露给 Agent；
- 永久删除 Wiki 只允许用户手动执行并二次确认；
- 未来 Agent 的 Document 删除只在用户明确要求并确认后执行，不能借此隐藏或恢复
  Wiki 上下文。

## 9. Memory Proposal

Agent 不能直接修改用户长期信息。

每次运行结束后，可以提出：

```text
建议更新：

类型：当前状态
原内容：正在准备一轮面试
新内容：已完成一轮面试，准备下一轮
来源：本次对话
```

用户可以：

- 确认；
- 修改后确认；
- 暂缓；
- 拒绝。

确认后，旧状态进入历史，新状态生效。

P0 不实现 Skill 自动更新。Skill 改进建议放到 P1。

## 10. 最小决策卡

决策卡只保存：

- 问题；
- 本次使用的个人上下文；
- 主要选项；
- AI 分析；
- 用户最终选择；
- 重新评估条件；
- 后续结果。

不建设复杂提醒、任务管理和完整决策中心。

## 11. Agent Run

最小运行时间线：

```text
收到请求
→ 识别任务
→ 选择 Skill
→ 获取个人上下文
→ 调用模型或工具
→ 生成结果
→ 产生 Memory Proposal
→ 完成运行
```

每一步至少展示：

- 步骤名称；
- 状态；
- 时间；
- 输入类型；
- 可公开结果摘要；
- 错误或取消原因。

不展示模型隐藏思维过程。

内部观测同样不展示完整 Prompt、完整用户内容、Secret、Cookie、连接串、未脱敏工具
输入输出或其他敏感信息。

## 12. 标准运行流程

```text
用户请求
→ 判断是否显式指定 Skill
→ 自动路由或采用用户选择
→ 获取相关 Wiki Item 和 Markdown 片段
→ 检查过期、冲突和缺失
→ 执行 Skill
→ 流式输出结果
→ 生成决策卡和 Memory Proposal
→ 用户确认
→ PostgreSQL 写入
→ Wiki 自动更新
```

一次运行最多选择一个主 Skill；Direct Answer 没有主 Skill。当前不做多 Skill 自动
协作。

## 13. P0 范围

1. 统一 Web 对话；
2. 决策 Skill；
3. 现有命理 Skill；
4. 自动 Skill 路由；
5. `/decision` 与 `/fortune`；
6. Skill 标签和选择来源；
7. 最小 Wiki Item；
8. 导入一篇 Markdown；
9. 上下文查看；
10. Memory Proposal 和用户确认；
11. 一张最小决策卡；
12. Agent Run 时间线；
13. 流式输出、失败、取消和重试；
14. 关键链路自动测试。

## 14. P1 范围

- 股票 Skill；
- 完整复盘；
- Markdown 批量导入导出；
- Obsidian 单向同步；
- 独立进化收件箱；
- Skill 改进建议和版本；
- Codex/CLI 接入；
- 多模型接入；
- 跨设备恢复。

## 15. 当前明确不做

- 六个完整一级页面；
- 每个 Skill 独立数据库；
- 永久展示一排 Skill 按钮；
- 多 Skill 自动编排；
- Skill 自动修改和发布；
- 实时双向 Obsidian 同步；
- 完整股票和健康系统；
- 知识图谱；
- 多 Agent；
- 多模型同时讨论；
- 面向公众的复杂权限。

## 16. 唯一验收链路

```text
1. Wiki 已保存“正在准备 Agent 岗位秋招”
2. 用户导入一篇面试复盘 Markdown
3. Agent 提取候选信息，用户确认
4. 用户询问“下一轮优先准备系统设计还是算法”
5. Agent 自动选择决策 Skill
6. 页面展示 Skill 和所用个人上下文
7. Agent 流式返回分析
8. Agent Run 展示真实执行步骤
9. Agent 生成“当前薄弱点”更新建议
10. 用户确认后 Wiki 更新
11. 用户保存最终选择
12. 下一次对话使用更新后的信息
```

这条链路稳定完成，MVP 即成立。

## 17. 秋招技术验收

项目需要能够解释并演示：

| 产品能力 | 技术主题 |
| --- | --- |
| 一个 Agent 多个 Skill | 路由、工作流抽象 |
| 自动路由与 `/` 覆盖 | 结构化选择、Fallback |
| 命理排盘 | Tool Calling、确定性能力 |
| Markdown 导入 | 文档解析、信息提取 |
| 上下文查看 | 检索、过滤、Context Assembly |
| Memory Proposal | Human-in-the-loop、事务写入 |
| 决策卡 | 业务建模、上下文引用 |
| Run 时间线 | SSE、事件、Trace、状态机 |
| 失败和重试 | 幂等、取消、故障恢复 |
| 模型调用 | Model Gateway、Provider 解耦 |

## 18. 配套交付

除产品功能外，还需要：

- 一份能够快速启动项目的 README；
- 一张清晰架构图；
- 一条稳定演示脚本；
- 关键技术决策记录；
- 核心链路自动测试；
- 常见失败场景说明；
- 面试时可讲解的项目演进故事。

## 19. 推荐开发顺序

开发不作为一次覆盖全部 Task 的长程执行，而按以下业务轮次交付：

| 轮次 | 产品结果 |
|---|---|
| ROUND-01 | 对话、刷新、取消、失败和 Citation 形成可信运行链路 |
| ROUND-02 | 一个助手承载 Direct/Research/Fortune，并提供用户 Runs 和内部观测 |
| ROUND-03 | 用户维护 Wiki、导入 Markdown、确认 AI 提取和控制个人上下文 |
| ROUND-04 | 使用个人上下文完成 Decision 秋招 MVP 12 步闭环 |
| ROUND-05 | P1 Review 使用真实结果形成复盘和待确认更新 |

每个轮次内部逐 Task 即时 Review；轮次结束后再完整执行该轮用户旅程、上一轮核心
回归和局部回滚/重新启用演练。只有完整验收通过才形成稳定基线，然后停止并等待用户
决定是否进入下一轮。

业务回滚优先关闭当前上层能力并保留下层与用户数据，不通过删除 Wiki、Decision、
Review 或执行破坏性数据库降级实现。具体执行契约见
[`业务交付轮次`](../../collaboration/rounds/README.md)。
