## 0. 文档目的

本文档定义启点作为第一种产品形态时，完整 Web MVP 应具备的用户体验和产品能力。

- [`启点完整产品蓝图`](future-product.md) 描述长期终局。
- 本文档描述终局之前的完整 Web 产品阶段。
- [`启点秋招最小 MVP`](recruiting-mvp.md) 是本文档的实现子集，用于当前秋招阶段优先交付。

## 1. Web MVP 定义

启点 Web 是一个**可使用、可观察、可持续沉淀的个人 Web Agent**。

它需要完整支持：

```text
提出问题
→ 选择 Skill
→ 使用相关个人上下文
→ 调用模型和工具
→ 展示结果与运行过程
→ 提出长期信息更新建议
→ 用户确认
→ 更新个人 Wiki
→ 形成决策与复盘
```

Web 是未来启点 Core 的第一个客户端，页面不应拥有一套无法被其他入口复用的 Agent 逻辑。

## 2. 产品目标

### 2.1 建立完整 Web 体验

让用户通过一个产品完成对话、信息管理、决策、复盘和 Agent 过程查看。

### 2.2 验证个人上下文价值

证明用户记录过的信息，可以在未来真实问题中被准确、相关地使用。

### 2.3 验证一个 Agent 多个 Skill

命理、决策和后续股票等能力共享同一个用户、上下文、记忆和运行体系。

### 2.4 建立持续进化闭环

一次对话能够产生个人信息、个人规则、决策或 Skill 改进建议，并在用户确认后影响下一次使用。

### 2.5 为 Skill Core 留下基础

未来接入 Codex、CLI 和其他模型时，不需要重新实现上下文、Skill 和记忆逻辑。

## 3. 当前目标用户

当前首先服务产品创建者本人。

典型需求包括：

- 管理股票、健康、面试和命理等个人信息；
- 不再重复向 AI 介绍背景；
- 让 AI 使用最新状态和个人规则；
- 保存重要决策和真实结果；
- 将 Obsidian Markdown 带入 Web；
- 观察 Agent 实际做了什么；
- 为未来 Codex 和其他模型保留统一上下文。

当前不以公共产品增长、多用户协作和商业化为主要目标。

## 4. 首要使用场景

### 4.1 命理

用户使用已保存或临时输入的出生信息完成排盘和解释，并能够区分确定性结果与 AI 解读。

### 4.2 现实决策

用户提出职业、项目、生活等选择。Agent 使用当前状态、目标和规则，输出选项、收益、代价、未知项和重新评估条件。

### 4.3 信息记录

用户在自然对话中表达新的事实、状态或规则，Agent 提出结构化保存建议。

### 4.4 Markdown 沉淀

用户导入 Obsidian Markdown，保留原文，并从中提取可以进入个人 Wiki 的候选信息。

### 4.5 股票

在基础闭环稳定后，接入持仓、成本、投资规则和历史决策，验证会持续变化的结构化个人数据。

## 5. Web 产品结构

完整 Web MVP 包含六个产品空间。

### 5.1 对话

统一 Agent 入口，完成提问、Skill 使用、上下文查看、工具调用和结果生成。

### 5.2 我的 Wiki

浏览和管理事实、当前状态、个人规则、AI 分析、领域数据和 Markdown。

### 5.3 决策与复盘

查看一次问题的选项、依据、最终选择、重新评估条件和真实结果。

### 5.4 进化收件箱

统一处理：

- 个人信息更新；
- 当前状态更新；
- 个人规则更新；
- 决策与复盘沉淀；
- Skill 改进建议。

### 5.5 Agent Runs

查看一次运行中真实发生的步骤、状态、工具、结果和错误。

### 5.6 Skills

查看已安装 Skill、当前版本、所需上下文、工具、数据范围和改进建议。

## 6. Skill 交互

### 6.1 自然语言自动路由

用户直接描述问题，Agent 根据任务自动选择主 Skill。

### 6.2 `/` 显式触发

用户输入 `/` 查看可用 Skill，并可以明确指定：

```text
/decision
/fortune
/stock
/research
```

### 6.3 快捷卡片

首页可以用少量快捷卡片帮助用户理解产品能力，但不长期展示一排 Skill 按钮。

### 6.4 Skill 标签

无论自动还是显式触发，回答都展示：

- 本次使用的主 Skill；
- 由用户指定还是自动选择；
- 使用了多少条个人信息；
- 是否调用工具；
- 是否可以更换 Skill 重新运行。

### 6.5 路由不确定性

| 判断 | 行为 |
| --- | --- |
| 高置信度 | 自动选择并执行 |
| 中等置信度 | 建议一个 Skill，由用户确认 |
| 低置信度 | 使用普通对话 |

上下文检索、Markdown 解析、Memory Curator 和写入等内部能力不作为用户可选 Skill，只在 Run 中展示。

## 7. 对话页

### 必须展示

- 用户消息和 Agent 回复；
- 当前 Skill；
- 运行状态；
- 本次使用的个人上下文；
- 工具调用及状态；
- 最终回答或 Artifact；
- 本次产生的更新建议。

### 必须支持

- 自然语言提问；
- `/` 选择 Skill；
- 展开上下文；
- 查看工具结果；
- 接受、修改、暂缓或拒绝更新建议；
- 将讨论保存为决策；
- 查看对应 Agent Run。

## 8. 我的 Wiki

Wiki 是个人信息的产品视图，不是独立的第二份数据。

一个页面可以组合：

- Wiki Item；
- 领域业务数据；
- 历史决策；
- Markdown Document；
- AI 分析。

### 8.1 Wiki Item

| 类型 | 示例 |
| --- | --- |
| 已确认事实 | 出生时间、当前工作 |
| 当前状态 | 正在面试、当前持仓 |
| 个人规则 | 单一股票仓位上限 |
| AI 分析 | 当前可能更重视稳定性 |
| 历史记录 | 已结束的工作或计划 |

每条信息至少包含：

- 内容；
- 类型；
- 领域；
- 来源；
- 更新时间；
- 当前状态；
- 用户确认状态。

用户可以新增、编辑、确认、标记过期、删除并查看历史来源。

### 8.2 Markdown Document

适合保存：

- 股票研究报告；
- 健康日记；
- 面试复盘；
- 命理解读；
- 个人总结。

每篇文档至少包含标题、Markdown 正文、来源、原始路径、领域、更新时间和相关对象。

## 9. Markdown 与 Obsidian

### 9.1 导入

```text
导入 Markdown
→ 保存原始文档
→ AI 提取候选事实、状态和规则
→ 用户确认
→ 写入个人 Wiki
```

原始文档不自动成为已确认事实。

### 9.2 导出

支持：

- 导出单篇文档；
- 导出一个领域；
- 导出决策和复盘；
- 导出完整个人 Wiki。

### 9.3 当前同步边界

完整 Web MVP 先支持导入导出，再验证 Obsidian 单向同步，不直接进入实时双向同步。

如果用户重新导入被修改的文件，它先成为更新建议，不直接覆盖数据库。

## 10. 决策与复盘

一条决策包含：

- 想解决的问题；
- 当时的个人状态；
- 本次使用的上下文；
- 可选方案；
- 收益、代价和未知项；
- AI 分析；
- 用户最终选择；
- 重新评估条件；
- 实际结果；
- 复盘结论。

决策引用的是当时使用的信息版本，后续个人状态变化不应改变历史决策依据。

## 11. 进化收件箱

每次运行后，Agent 可以产生：

```text
个人信息更新
当前状态更新
个人规则更新
决策与复盘
Skill 改进建议
```

用户可以接受、修改、暂缓或拒绝。

### 11.1 长期信息

经用户确认后写入个人 Wiki，并保留来源和历史版本。

### 11.2 Skill 改进

Skill 改进先形成 Proposal，经过查看、验证和版本更新后才能启用。

Agent 不能根据一次对话自动修改并发布 Skill。

## 12. 首批 Skill

### 12.1 命理 Skill

- 获取出生信息；
- 使用确定性工具排盘；
- 区分排盘事实与解释；
- 返回可展示 Artifact；
- 经用户确认后保存长期信息。

### 12.2 决策 Skill

- 读取相关事实、状态和规则；
- 展示所用上下文；
- 输出选项、收益、代价、反例和未知项；
- 不替用户自动选择；
- 创建决策并支持复盘。

### 12.3 通用对话与调研

用于普通问题和资料补充，共享同一 Agent 运行链。

### 12.4 股票 Skill

作为完整 Web MVP 的首个领域扩展，接入持仓、成本、规则、观察标的和历史决策。

## 13. Skill 与个人信息

Skill 与个人 Markdown 分开存放。

- Skill 描述怎样工作；
- 个人 Wiki 描述用户当前情况；
- 个人规则约束 Skill；
- 决策和复盘验证实际效果。

Skill 不直接访问具体数据库或 Obsidian，而是声明需要什么上下文，由 Core 提供。

不同 Skill 在同一数据库中逻辑隔离，不为每个 Skill 部署独立物理数据库。

## 14. 标准 Agent 运行

```text
用户请求
→ 判断显式 Skill 或自动路由
→ 获取相关个人上下文
→ 检查过期、冲突和缺失
→ 调用模型与工具
→ 返回回答和 Artifact
→ 生成记忆、决策或 Skill 更新建议
→ 用户确认
→ 写入数据库
→ Wiki 自动展示
→ 更新检索索引和 Markdown 导出
```

早期一次运行只选择一个主领域 Skill，并可以组合一个通用工作流，不做任意多个 Skill 自动协作。

## 15. Agent Runs

运行页展示真实系统动作，不展示模型隐藏思维过程。

### 最小时间线

```text
收到请求
→ 识别任务
→ 选择 Skill
→ 获取个人上下文
→ 调用模型或工具
→ 生成结果
→ 产生沉淀建议
→ 完成运行
```

每一步至少展示名称、状态、时间、输入类型、结果摘要以及错误或取消原因。

## 16. 数据原则

### PostgreSQL

作为线上业务事实源，保存：

- Wiki Item；
- Markdown Document 及元数据；
- 决策与复盘；
- 领域数据；
- 更新建议；
- 对话和产品 Run。

### 逻辑隔离

- 用户长期事实集中管理；
- 领域数据按 Skill 范围隔离；
- Skill 中间数据与用户事实分开；
- Runtime 状态与长期记忆分开；
- 向量索引是派生数据。

### 用户可见性

凡是会长期影响未来回答的个人信息，都必须有用户可查看、修改和删除的表达。

## 17. 为未来 Core 保留的边界

1. Web 只负责交互和展示。
2. Skill 不直接修改长期数据。
3. 个人信息通过统一上下文入口访问。
4. 模型调用集中管理。
5. Agent 运行形成统一事件。
6. 所有长期对象具有稳定 ID、来源、时间和版本。
7. Skills、个人数据和 Runtime 分开管理。

## 18. 完整 Web MVP 范围

### 必须具备

1. 统一对话；
2. 自动路由和 `/` 显式 Skill；
3. 命理、决策和通用调研能力；
4. Skill 与上下文展示；
5. Wiki Item；
6. Markdown 创建、导入和导出；
7. 进化收件箱；
8. 决策与复盘；
9. Agent Run 时间线；
10. Skill 查看和版本信息；
11. 流式输出、取消、失败和重试；
12. 关键链路自动测试。

### 紧随其后

- 股票 Skill；
- Obsidian 单向同步；
- Skill 改进 Proposal；
- Codex/CLI 连接同一上下文；
- 第二个模型接入。

## 19. 当前不做

- 每个 Skill 独立数据库；
- 实时双向 Obsidian 同步；
- Skill 自动修改和发布；
- 隐藏的长期模型画像；
- 多 Agent 自由协作；
- 多模型同时讨论；
- 知识图谱；
- 完整股票交易平台；
- 完整健康管理系统；
- Skill 市场；
- 面向公众的复杂权限。

## 20. 验收场景

### 命理

用户发起命理问题，Agent 获取出生信息、调用排盘工具、区分事实与解释，并在确认后保存信息。

### 决策

用户基于已保存的状态和规则提出选择，Agent 展示上下文、生成分析，并保存最终选择和重新评估条件。

### Markdown

用户导入一篇面试复盘，系统保留原文，提取候选信息，并在确认后更新个人 Wiki。

### 信息变化

用户表达当前状态变化，进化收件箱展示更新建议，确认后旧状态进入历史、新状态生效。

### 运行失败

工具失败时，Run 页面展示失败步骤，用户可以重试，失败运行不写入错误长期信息。

## 21. 成功标准

### 产品成功

- 用户愿意持续记录个人信息；
- AI 能使用正确、最新且相关的上下文；
- 用户明显减少重复介绍背景；
- Markdown 中的信息能被可靠沉淀；
- 对话能够形成决策与真实复盘；
- 用户变化后，下一次回答能够体现变化。

### 架构成功

- 新增 Skill 不需要新增另一套页面和执行链；
- Skill 不依赖具体存储；
- 会话、长期记忆和 Runtime 状态清楚分开；
- Web 展示来自统一 Agent Run；
- 失败、取消和重试不会制造错误业务结果；
- 未来 CLI 可以复用同一套 Core。

## 22. 分阶段建设

```text
阶段 1：完成秋招最小 MVP
阶段 2：补齐独立决策、进化收件箱和 Skills 页面
阶段 3：完善 Markdown 导入导出和复盘
阶段 4：增加股票 Skill
阶段 5：接入 Obsidian 单向同步
阶段 6：让 Codex/CLI 使用同一 Core
```

秋招最小 MVP 是本方案的优先子集，完整 Web MVP 不应反向阻塞当前交付。
