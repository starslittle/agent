## 0. 文档目的

本文档定义启点最终希望成为怎样的产品，以及个人信息、Markdown、Skill、Agent 和不同使用入口之间的关系。

- [`产品定位`](positioning.md) 用于快速理解启点是什么。
- 本文档描述完整终局，不代表当前版本必须全部实现。
- [`Web MVP 产品需求`](web-mvp.md) 定义完整 Web 产品阶段。
- [`秋招最小 MVP`](recruiting-mvp.md) 定义当前优先实现的 Web MVP 子集。
- [`Agent Runtime 目标架构`](../architecture/agent-runtime.md) 定义代码和运行时如何支撑产品。

## 1. 最终产品定义

启点最终是一个**属于用户自己的个人 AI 身份与上下文系统**。

用户通过同一个启点账号，在 Web、Codex、CLI、其他电脑或其他 AI 应用中，继续使用同一份个人信息、当前状态、规则、历史决策和 Skill 配置。

启点不是让每个 AI 分别记住用户，而是让不同 AI 在获得允许后，使用同一份持续更新的个人上下文。

最理想的用户感受是：

> 我换了一台电脑、换了一个模型、换了一个应用，但它仍然知道现在的我是谁、我正在做什么，以及我希望它怎样帮助我。

## 2. 一句话定位

> 启点是你的个人 AI 身份与决策系统，让不同 AI 使用同一份持续更新的个人上下文。

面向当前用户的简化表达：

> 让 AI 真正了解现在的你，再和你一起做决定。

## 3. 用户问题

### 3.1 信息散落

个人资料分散在对话、笔记、Markdown、表格和不同应用中，没有一份可以被 AI 稳定使用的当前状态。

### 3.2 每次重新介绍自己

用户切换设备、对话或模型后，需要重复解释背景、目标、规则和最近发生的变化。

### 3.3 保存过不等于现在有效

股票持仓、健康、面试、工作和计划都会变化。普通文档很难自动判断哪条信息代表现在。

### 3.4 对话没有形成长期积累

一次讨论可能很有价值，但其中的事实、决策、结果和经验不会自然进入下一次任务。

### 3.5 Skill 与个人变化脱节

Skill 描述 Agent 应该怎样工作，但如果它无法获得用户的最新状态和规则，仍然只能给出通用答案。

### 3.6 个人信息被模型和应用割裂

Codex、Web Agent 和其他模型可能各自维护一套记忆，用户无法确认哪一份才是当前真实版本。

## 4. 产品目标

启点长期要完成六件事：

1. 建立一份由用户拥有、持续更新的个人上下文。
2. 让 AI 每次只使用当前任务真正相关的信息。
3. 让 Web、Codex、CLI 和其他应用连接同一个启点账号。
4. 让不同 Skill 围绕同一份个人信息协同工作。
5. 将“分析—决定—行动—结果—复盘”连接成长期闭环。
6. 将真实使用中的经验沉淀为个人规则，并在必要时改进 Skill。

## 5. 两种产品形态

### 5.1 启点 Web

Web 是完整用户体验和第一客户端，负责：

- 日常对话；
- 查看个人 Wiki；
- 导入和导出 Markdown；
- 查看本次使用的 Skill 和个人上下文；
- 确认个人信息更新；
- 保存决策与复盘；
- 查看 Agent 运行过程；
- 管理 Skill 和改进建议。

Web 也是当前阶段学习和展示 Agent 架构的主要产品。

### 5.2 启点 Core

Core 是不同入口共同使用的个人上下文与 Agent 能力层，负责：

- 识别任务；
- 选择 Skill；
- 获取相关个人信息；
- 检查信息是否过期、冲突或缺失；
- 调用模型和工具；
- 形成记忆、决策和 Skill 更新建议；
- 为 Web、Codex、CLI 和其他 Agent 提供一致能力。

Core 的早期形态可以是公共流程与 Skill 约定。只有真实需求出现后，才逐步形成独立 CLI、服务和开放接口。

### 5.3 两种形态的关系

```text
启点 Web ─────┐
Codex / CLI ──┼──→ 启点 Core ──→ Skill / 模型 / 工具
其他 AI 应用 ─┘          ↕
                    启点账号
               个人上下文与决策历史
```

Web 不拥有一套独立 Agent 逻辑，Codex 也不维护另一份长期个人记忆。

## 6. 启点账号

启点账号不是普通登录账号，它承载用户的个人 AI 身份。

### 6.1 身份信息

- 基础资料；
- 长期经历；
- 职业背景；
- 重要关系；
- 长期目标。

### 6.2 当前上下文

- 当前持仓；
- 当前工作和面试状态；
- 当前健康状态；
- 当前计划；
- 正在处理的问题；
- 近期现实限制。

### 6.3 个人规则

- 投资纪律；
- 风险偏好；
- 职业选择标准；
- 个人价值排序；
- 不同领域的使用边界；
- Agent 应遵守的长期原则。

### 6.4 决策与复盘

- 当时的问题和状态；
- 使用的个人信息；
- 最终选择；
- 重新评估条件；
- 实际结果；
- 复盘后的认识。

### 6.5 Agent 配置

- 已安装 Skill；
- Skill 当前版本；
- 个人 Skill 配置；
- 常用模型和工具；
- 上下文使用偏好。

## 8. 数据、Wiki 与 Markdown

三者不是竞争关系，而是承担不同职责。

### 8.1 数据库是事实源

数据库保存需要准确更新、查询和关联的内容：

- 当前状态；
- 已确认事实；
- 个人规则；
- 领域业务数据；
- 决策与复盘；
- 信息来源和版本。

第一阶段使用同一个 PostgreSQL，通过领域和用途逻辑隔离，不为每个 Skill 部署独立数据库。

### 8.2 Wiki 是产品视图

Wiki 将数据库记录和 Markdown 文档组合成用户容易理解的页面。

例如股票 Wiki 可以同时展示：

- 当前持仓；
- 投资规则；
- 历史交易；
- 最近决策；
- 股票研究文档；
- AI 分析。

Wiki 不维护另一份独立数据，也不需要在数据库更新后再次手工同步。

### 8.3 Markdown 是开放文档

Markdown 适合保存：

- 股票研究报告；
- 健康日记；
- 面试复盘；
- 命理解读；
- 个人总结；
- 从 Obsidian 导入的长篇内容。

Markdown 也是数据导入、导出和长期可携带格式。

### 8.4 统一关系

> 数据库负责“现在是什么”，Markdown 负责“完整说过什么”，Wiki 负责“用户怎样理解和管理它们”。

## 9. 个人信息类型

| 类型 | 含义 |
| --- | --- |
| 原始来源 | 用户消息、导入文档、工具结果 |
| 已确认事实 | 用户确认且当前可以使用的信息 |
| 当前状态 | 会随时间变化，需要判断新旧的信息 |
| 个人规则 | 用户希望 Agent 长期遵守的原则 |
| AI 分析 | 模型根据当前证据形成的推断 |
| 决策与结果 | 用户实际做出的选择和后续结果 |

每条长期信息都应尽量具有来源、更新时间、当前状态和确认状态。

AI 分析不能静默升级为事实，历史状态不能直接代表现在。

## 10. 记忆分层

### 10.1 用户可见长期记忆

凡是会持续影响未来回答的信息，都必须有用户可查看、修改和删除的表达：

- 事实；
- 状态；
- 规则；
- 目标；
- 决策；
- 长期 AI 分析。

### 10.2 Skill 工作数据

Skill 可以保存中间计算、缓存、临时摘要和 Artifact，但这些内容不自动成为用户事实。

### 10.3 Agent Runtime

对话、Run、事件和 Checkpoint 用于维持和恢复一次运行，不等于用户长期记忆。

### 10.4 检索索引

全文和向量索引用于寻找相关内容，可以删除和重建，不能成为唯一事实源。

核心原则：

> 模型可以拥有临时工作状态，但不能拥有用户看不到、却长期影响决策的隐藏个人画像。

## 11. Skill 系统

Skill 与个人 Markdown 分开存放。

- Skill 描述 Agent 应该怎样分析和行动；
- 个人 Wiki 描述用户当前是什么状态；
- 个人规则连接 Skill 与用户；
- 决策和复盘记录真实效果。

### 11.1 通用 Skill

- 调研；
- 决策；
- 计划；
- 复盘。

### 11.2 领域 Skill

- 股票；
- 健康；
- 面试与职业；
- 命理。

### 11.3 Skill 共同约定

每个 Skill 应说明：

- 需要哪些个人上下文；
- 默认允许读取哪些领域；
- 使用哪些工具；
- 输出什么结果；
- 可以提出哪些长期信息更新；
- 什么情况视为完成。

Skill 不直接拥有用户数据，只能通过 Core 请求相关上下文，并提交更新建议。

### 11.4 Skill 数据隔离

不同 Skill 采用逻辑隔离：

- 共享基础资料、目标和通用规则；
- 领域数据默认只向对应 Skill 开放；
- 决策 Skill 按当前任务获取用户允许的领域；
- Skill 私有缓存和中间状态只由对应 Skill 使用。

只有未来出现不可信第三方 Skill 或特殊隔离要求时，才考虑物理分库。

### 11.5 Agent 文档操作

启点 Core 的目标能力包括对用户授权文档进行创建、读取、修改和删除。它与 Wiki
长期事实更新、文档隐藏是三套不同权限：

- 用户明确要求时，Agent 可以创建或修改文档，并保存 Changeset 和 Revision；
- Agent 自主推断出的修改先交给用户确认；
- Agent 删除文档必须来自明确用户指令、目标唯一并再次确认，删除后不可恢复；
- 暂时隐藏和恢复只允许用户在页面手动操作，Agent 没有对应 Capability；
- Wiki 的推断性更新继续通过 Proposal，Document Capability 不能直接改写长期事实。

具体进入哪个产品阶段尚未确定，不能由当前 Markdown 导入 Task 顺手实现。

## 12. 标准 Agent 运行

```text
用户提出问题
→ Core 识别任务
→ 选择最多一个主 Skill，或直接回答
→ 获取相关个人上下文
→ 检查信息新旧、冲突和缺失
→ Skill 调用模型与工具
→ 返回回答和 Artifact
→ 生成信息、规则、决策或 Skill 更新建议
→ 用户确认
→ 写入唯一事实源
→ Wiki 自动展示最新内容
→ 检索索引和 Markdown 导出按需更新
```

第一阶段不追求任意多个 Skill 自动协作。一次任务以一个主领域 Skill 为主，可以组合一个通用工作流。

## 13. 持续进化闭环

启点真正需要优化的是“从一次使用到下一次使用”的学习过程。

### 13.1 个人状态更新

例如持仓变化、面试进入下一轮或健康状态改变，写入当前状态和历史记录。

### 13.2 个人规则更新

例如形成新的投资纪律或职业选择标准，写入个人规则，并在下一次任务中自动使用。

### 13.3 Skill 更新

当 Agent 的工作方法本身需要改变时，形成 Skill 改进建议。

Skill 不应根据一次对话自动改写，而应经过：

```text
发现问题
→ 形成改进建议
→ 查看修改内容
→ 案例验证
→ 产生新版本
→ 启用或回滚
```

### 13.4 进化收件箱

所有待沉淀内容进入统一收件箱：

- 个人信息更新；
- 个人规则更新；
- 决策记录；
- 复盘结论；
- Skill 改进建议。

用户可以接受、修改、暂缓或拒绝。

## 14. 决策与复盘

一条决策至少包括：

- 想解决的问题；
- 当时的个人状态；
- 本次使用的上下文；
- 可选方案；
- 收益、代价和未知项；
- AI 分析及其不确定性；
- 用户最终选择；
- 重新评估条件；
- 实际结果；
- 复盘后的规则和认识。

经过真实结果验证的经验，才进入下一次决策。

## 15. 跨设备和跨应用

### 15.1 更换设备

用户登录同一个启点账号，恢复个人上下文、Skill 配置和决策历史。

### 15.2 更换 Agent

Codex、CLI 或其他 Agent 连接启点账号，按任务获取相关上下文，并将更新建议返回启点。

### 15.3 连接其他应用

未来其他应用可以提供“连接启点”入口。用户选择允许使用的范围，例如职业、股票或健康。

应用获得的是当前任务所需的 Context Pack，而不是用户全部数据。

### 15.4 离开启点

用户可以导出 Markdown 和结构化数据，带走个人信息、文档、决策和规则。

## 16. Obsidian

### 第一阶段

- 导入 Markdown；
- 保留原始文档和路径；
- AI 提取候选事实、状态和规则；
- 用户确认后进入个人 Wiki；
- 按领域或完整导出 Markdown。

### 后续阶段

- 单向自动同步；
- 文件版本识别；
- 冲突提示；
- 最后再考虑双向同步。

Obsidian 与 Web 不应同时成为同一条结构化事实的事实源。

## 17. 产品原则

1. 用户拥有并能够带走个人信息。
2. 数据库是事实源，Wiki 是视图，Markdown 是开放格式。
3. Skill 与个人信息分开存放，运行时动态组合。
4. 使用相关信息，不默认把全部数据交给模型。
5. 事实、状态、规则和 AI 分析必须分开。
6. 长期写入需要用户确认。
7. 模型可以替换，个人上下文必须延续。
8. Skill 可以改进，但不能无审核地自我修改。
9. 不同 Skill 逻辑隔离，不在早期物理分库。
10. AI 辅助用户决定，不替用户承担最终选择。

## 18. 演进路线

Agent Core 的 ExecutionPlan、多 Skill、支持能力、通用 Bounded Action Loop、Run 内
持久 Human-in-the-loop、高级上下文规划和 Eval 治理仍是候选设计，统一记录在
[`Agent Core 未来扩展候选`](../architecture/agent-core-future-options.md)。这些候选
尚未形成产品承诺，不属于当前秋招 MVP 或现有业务轮次。

```text
阶段 1：启点 Web + 账号 + PostgreSQL 个人 Wiki
阶段 2：Markdown 导入导出 + 决策与复盘
阶段 3：股票等更多 Skill + 进化收件箱
阶段 4：Obsidian 单向同步 + Codex/CLI 接入
阶段 5：不同模型和应用连接同一个启点账号
阶段 6：形成开放的个人上下文协议
```

## 19. 长期成功标准

启点是否成立，不取决于保存了多少资料，而取决于：

- 用户是否明显减少重复介绍背景；
- AI 是否使用了正确、最新的个人信息；
- 用户能否理解和修正 AI 使用的上下文；
- 一次分析是否能够形成真实决策与复盘；
- 过去的记录是否在未来产生价值；
- 用户变化后，Agent 是否在下一次任务中体现变化；
- 更换设备、模型和应用后，个人上下文是否能够延续。

最终目标不是复制用户，而是建立一个能够随着用户持续变化的个人 Agent 系统。
