# ADR-010：Codex 与 Grok 的文件化协作协议

> 状态：accepted
>
> 日期：2026-07-30

## 背景

启点接下来会进行 Skill、统一助手、个人 Wiki 和决策闭环等跨前后端演进。任务同时
涉及产品语义、Runtime 边界、数据库状态机和前端体验。

团队希望发挥：

- Codex 在项目理解、架构、任务拆分、独立审查和真实用户旅程 E2E 上的作用；
- Grok 在快速编码、机械迁移、单元测试和模块级验证上的作用；
- 用户在产品优先级和重大取舍上的最终决定权。

仅通过聊天复制方案容易造成上下文丢失、范围扩大、文档漂移和无法审计的验收。

## 决策

在仓库中建立 Git 可追踪的 `collaboration/` 协作区：

```text
Codex 写 Task
→ Grok 按 Task 实现并写 Handoff
→ Codex 根据 diff 和验收标准做独立 Review
→ Codex 对用户可见或跨服务变更执行 Browser / Computer Use E2E
→ Grok 按 Review 修复
→ Codex 复验并接受
→ 用户决定是否合并或进入下一里程碑
```

长期产品与架构文档继续保存在 `docs/`，不复制到执行者专属目录。Task 通过路径和
基准提交引用这些权威文档。

文件所有权：

| 文件 | 默认写入者 |
|---|---|
| 产品、架构、ADR | Codex，在用户确认后 |
| Task | Codex |
| 业务代码、单元测试和模块级集成测试 | Grok |
| Handoff | Grok |
| Review、产品级 E2E 场景和最终技术验收 | Codex |
| 产品最终决定 | 用户 |

默认一个 Task 一个分支或 Git worktree。需要 review gate 的 Task 完成后必须停止，
不能自动执行下一个依赖 Task。

验证责任采用双层闭环：

1. Grok 证明代码层实现满足 Task：完成静态检查、单元测试和模块级集成测试；
2. Codex 证明产品链路真实可用：独立审查代码，并对用户可见或跨服务变更使用
   Browser / Computer Use 执行完整 E2E。

Grok 可以执行已固化的自动化 E2E 作为辅助证据，但其结果不能替代 Codex 的独立产品
验收。只有纯内部且尚未接入产品路径的基础 Task 可以声明产品级 E2E 不适用，并由
Codex 在 Review 中确认理由。

## 原因

- 将模糊产品意图冻结为可验收契约；
- 让执行者获得短、稳定、明确的上下文；
- 防止同一模型同时实现和自我验收；
- 避免两个 Agent 同时编辑同一文件；
- 使每轮实现、偏差、测试和审查都可追踪；
- 未来可以替换或增加执行 Agent，而不改变仓库架构。

## 后果

正面：

- Grok 可以集中于小范围快速实现；
- Codex 可以基于真实 diff 和真实用户操作做独立验收；
- 用户只需处理需要产品判断的阻塞；
- Task 可以逐步自动化。

代价：

- 每个非简单任务需要 Task 和 Handoff；
- 串行 review gate 会增加一次交接；
- 文档必须随架构决策维护。

## 约束

- 不把完整架构复制到 `collaboration/`；
- 不在 Handoff 或 Review 中保存 Secret、用户数据或完整运行日志；
- 执行者不能修改 Task 以使实现看起来通过；
- Reviewer 不能在未更新 Task/ADR 的情况下扩大验收范围；
- 执行者验证通过不等于产品级验收通过；
- 必需的 Codex E2E 未执行或失败时，Task 不能标记为 `accepted`；
- 发现产品决策缺失时返回用户，不由执行者猜测；
- 生产操作、破坏性迁移和外部发布仍需用户明确授权。
