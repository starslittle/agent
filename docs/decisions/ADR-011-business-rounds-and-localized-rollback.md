# ADR-011：按业务轮次交付并支持依赖感知的局部回滚

> 状态：accepted
>
> 日期：2026-07-30

## 背景

统一助手、Skill、Agent Runs、内部观测、个人 Wiki、Decision 和 Review 共包含 28 个
实现 Task。它们属于同一条产品演进路线，但不是一个单一业务需求。

如果把全部 Task 当作一次长程执行：

- 产品反馈要到最后才出现；
- 前序协议或交互错误会持续传递到后续业务；
- Codex/Grok 上下文、分支和验收证据会不断膨胀；
- 故障时难以判断影响面；
- 回滚容易退化为全量代码回退或危险的数据库降级。

用户确认希望把相互独立的业务能力解耦为多个交付轮次，每轮形成真实用户结果、完整
验收和稳定基线，出现问题时只关闭受影响的业务层。

## 决策

### 1. Task 与业务轮次是两个层级

- Task 是最小实现和 Review Gate；
- Business Round 是一组 Task 形成的可演示、可验收、可暂停业务增量；
- Task 完成后立即验收，业务轮次结束后再执行该轮完整用户旅程；
- 用户一次只授权一个业务轮次，某轮 `accepted` 不自动授权下一轮；
- 不创建一个包含全部 Task 的长程 Grok 分支或一次性执行任务。

### 2. 业务轮次

| 轮次 | 业务结果 | Task |
|---|---|---|
| ROUND-01 | 可信运行链路 | TASK-002～TASK-007 |
| ROUND-02 | 统一 Agent、Skill 与观测 | TASK-001、TASK-008～TASK-013、TASK-028 |
| ROUND-03 | 个人 Wiki、Markdown 与确认写入 | TASK-014～TASK-020 |
| ROUND-04 | Decision 秋招 MVP 闭环 | TASK-021～TASK-024 |
| ROUND-05 | Review 复盘闭环 | TASK-025～TASK-026 |
| RELEASE-GATE | 发布准备和人工生产门禁 | TASK-027 |

轮次之间存在有向依赖，但每轮必须可独立验收、可在结束后暂停，并形成稳定提交。
完整范围、验收脚本和回滚边界以
[`collaboration/rounds/`](../../collaboration/rounds/README.md) 为准。

### 3. 局部回滚优先

默认回滚顺序：

```text
关闭当前业务能力
→ 回到上一轮 accepted 部署/提交
→ 必要时回退当前轮代码
```

不把数据库 Down Migration、删除用户数据或全量 Git 回退作为首选事故处理手段。

每个轮次在进入 `ready` 前必须冻结：

- 服务端权威的能力开关或等价流量切换机制；
- 前端隐藏、后端拒绝和依赖检查行为；
- 上一轮稳定部署/提交；
- 新增 Schema 的前向兼容和停用行为；
- 回滚步骤、停止条件和成功判据；
- 禁止单独关闭的下游依赖。

前端开关只负责体验，不是权限或安全边界。后端必须拒绝已关闭能力的新请求。

有效能力由 Go 产品策略、用户/环境权限、依赖就绪状态和 Python Skill/Runtime
readiness 共同决定。Python 的 Skill `available` 不替代 Go 的产品开关。创建 Run
时冻结有效能力和版本快照；关闭能力默认阻止新 Run/新写入，运行中请求按照本轮预先
冻结的完成、取消或强制停止策略处理。

### 4. 回滚遵守依赖方向

能力层级：

```text
可信 Runtime
→ 统一 Agent
→ 个人 Wiki
→ Decision
→ Review
```

上层能力出问题时只关闭上层，保留下层。例如 Review 可以独立关闭而不影响 Decision；
Decision 可以关闭而保留 Wiki。

不能在下游仍启用时关闭其强依赖。例如 Decision 已启用时不能关闭 Wiki Context
并假装 Decision 仍完整可用。需要关闭底层时，必须同时关闭依赖它的所有上层能力，
即执行依赖闭包回滚。

内部观测是 ROUND-02 的只读能力。它可以独立关闭而不影响用户 Agent Runs；但后续
轮次验收前必须存在其他等价诊断手段，不能在完全不可观测的状态下继续扩大变更。

### 5. 数据采用 Expand–Migrate–Contract

- 当前轮优先增加新表、新字段、新索引和兼容读取；
- 新旧代码在约定兼容窗口内都能读取必要数据；
- 关闭新能力时保留已写入数据和 Revision，不静默删除或改写；
- destructive contract、旧字段删除和不可逆清理必须进入单独 Task；
- 兼容代码至少保留到下一个依赖业务轮次验收通过，或由专门清理 Task 明确证明可以
  删除；
- 回滚演练默认验证“旧行为 + 新 Schema”能够安全工作，而不是执行 Schema 降级。

### 6. 稳定基线

每轮完成后记录：

- round base commit；
- 每个 Task 的 accepted Review；
- 自动测试摘要；
- Codex Browser / Computer Use 轮次 E2E；
- Migration 与能力开关清单；
- 回滚演练结果；
- accepted commit，可选稳定 Tag；
- 已知问题和下一轮是否获用户授权。

单个 Task 继续使用独立 Grok worktree/branch。accepted Task 按顺序进入当前稳定主线，
不为整个业务轮次维护长期分叉的实现分支。

## 原因

- 产品可以在每个真实价值台阶上获得反馈；
- 错误更早暴露，修复时所需上下文更小；
- 每轮都有清晰的故障域、数据边界和关闭方式；
- Wiki、Decision、Review 等用户数据不会因上层功能回退而被破坏；
- Codex 的完整 E2E 聚焦当前业务，不需要每个小 Task 重复全量链路；
- Grok 仍可在明确的小 Task 内快速实现。

## 后果

正面：

- 可以只回滚最新或故障业务层；
- 每轮完成后都能停下来体验和重新排优先级；
- 发布、诊断和验收证据更容易定位；
- 避免一次长程执行造成方案漂移。

代价：

- 每轮需要能力控制、验收记录和回滚演练；
- 兼容窗口会短期保留少量旧代码；
- 依赖闭包意味着底层能力不能在上层启用时任意关闭；
- 数据库 Contract 清理会晚于业务功能交付。

## 约束

- 用户未授权时不自动进入下一业务轮次；
- Task `accepted` 不等于业务轮次 `accepted`；
- 业务轮次 `accepted` 不等于生产发布获批；
- 不用前端隐藏代替服务端能力控制；
- 不用数据库 Down Migration 作为常规功能回滚；
- 不删除已确认用户数据来制造“回滚成功”；
- 未完成回滚演练和完整轮次 E2E 时，轮次不能标记为 `accepted`。
